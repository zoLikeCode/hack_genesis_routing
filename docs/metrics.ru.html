Метрики и стратегии выбора провайдера

Hard constraints → метрики → стратегии → нормированный профиль → выбор. Ограничения допуска обязательны и не могут быть компенсированы высоким soft-score.

Единая метрика качества

conversion оценивает вероятность получить approved на первоначальном запросе:

p = (A + κ × p₀) / (n + κ)
κ = 10
p₀ = conversion_24h, иначе 0.5
n = approved + rejected + expired первоначальных вызовов

Это регуляризованная частота, а не заявление о независимой байесовской выборке. Поздний approved после timeout не меняет первоначальный результат.

Причинное окно и сегменты

  1. Исключить текущий operation_id, будущие и записи старше 24 часов относительно операции.
  2. Оставить совместимые банк и сумму, отсортировать, затем взять последние 50.
  3. Искать сегмент минимум из 10 строк: банк+диапазон → банк → диапазон → провайдер.

Для сегмента:

p_rest = (A_rest + κ × p₀) / (n_rest + κ)
p_segment = (A_segment + γ × p_rest) / (n_segment + γ), γ = 10

Сам сегмент не входит в rest. Для provider-level используется первая формула по всему окну.

Дополнительного health-множителя нет. Нулевые/отрицательные активные веса и неизвестные ключи запрещены.

Доли

E(q) = ½ × Σ(qⱼ − rⱼ)²
improvementᵢ = E(before) − E(after assigning to i)

Улучшения нормируются между текущими кандидатами в [0,1]. Вектор содержит всех настроенных провайдеров, включая недоступных; их цели не перераспределяются. Fallback имеет цель 0 и не участвует в Ranker. Активные цели count/volume должны суммироваться в 100%.

Отчёт и проверка

provider_metrics отдельно показывает initial conversion/timeouts/refusals/answered success/p90 и final approved/rejected/unresolved. conversion_backtest последовательно прогнозирует результат до добавления строки и сравнивает Brier score с фиксированным published prior.

Brier-проверка использует только наблюдавшиеся попытки. Без исторических снимков conversion_24h она не доказывает преимущество маршрутизации и не даёт контрфактических исходов.
