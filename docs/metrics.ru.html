Зачем

Программист

Новая величина, которая должна влиять на выбор, — это метрика: ключ в Metrics::Inputs, значение, список METRICS у стратегии. Без веток в Engine. Timeout, отказ и p90 в окне — разные поля.

Аналитика

CSV целиком — history_baseline. Живое окно — provider_metrics. В attempts: профиль, вклады стратегий, scope, health, metric_disagreement. Рекомендации называют ключ YAML.

Бизнес

Доля, конверсия, обязательства и качество попыток — разные метрики, разные стратегии, один сравнимый счёт. Трафик уходит от молчащего партнёра без бана: health режет счёт, floor не обнуляет контракт.

Стратегия — комбинация метрик

Жёсткие фильтры (status, лимиты, банк) метриками стратегии не являются: они допускают или отсекают. Всё, что после допуска двигает выбор — метрика. Как её смешать с другими — стратегия. Одна метрика тоже стратегия (например conversion = clamp(conversion_24h)).

Ранжирование

Ranker считает окно один раз: тот же вектор — вклад historical_quality и множитель health. Выключить только стратегию недостаточно, чтобы убрать health: multipliers.health.enabled: false ставит множитель 1. Предпочтительный — max total среди допущенных основных. Ничья: меньший priority, затем имя. metric_disagreement — конфликт компонент окна, в argmax не входит. goal_disagreement — конфликт стратегий. Fallback вне Ranker.

Семейство окна

Четыре компоненты в [0, 1] — метрики источника window. Стратегия historical_quality их комбинирует; health — отдельная комбинация recent-среза.

На сегменте: n, nap, nrej, nexp. π = approval_prior (0.5), α = prior_strength (10), t₀ = timeout_prior (0.10), β = timeout_prior_strength (5).

(1) approvalâ = (nap + α · π) / (n + α)
(2) timeoutt̂ = (nexp + β · t₀) / (n + β)  availability = 1 − t̂
(3) acceptanceĉ = (nap + α · π) / (nap + nrej + α)

Expired нет в знаменателе acceptance: молчание ≠ отказ кассы. refusal_rate = nrej / n без сглаживания, в смесь не входит.

(4) latency p90 по answered с известной latency, rank = (m − 1) · 0.90 (линейная интерполяция).
latency = 1, если m = 0; иначе clamp[0,1](1 − p90 / Tbad), Tbad = 600 с.

Веса включённых компонент нормируются. Сейчас единственная комбинация — weighted_sum:

(5) смесь w̃c = wc / Σ wenabled  q = Σ w̃c · xc ∈ [0, 1]

Дефолт: approval 0.40, availability 0.25, acceptance 0.15, latency 0.20. Overlay одного веса сдвигает все w̃.

(6) сегмент κ = ns / (ns + γ), γ = 10  q = κ q(s) + (1 − κ) q(overall), если ns ≠ n

Для выбора (не отчёта) первый сегмент с n ≥ 5: bank_amount → bank → amount → provider. Коридоры: ≤5k / 15k / 50k / 100k / выше. Пустое окно: live_prior, q от π и t₀, p90 = nil.

(7) вклад score = clamp[−1,1](2q − 1)
(8) health b = availabilityrecent, если nap+nrej = 0 на срезе;
иначе b = (wA · av + wC · ĉ) / (wA + wC), дефолт 0.60 / 0.40.
health = f + (1 − f) · be, f = 0.25 ∈ (0, 1], e = 1 (у vipay overlay e = 1.5).

Recent — последние 10 строк уже отфильтрованного окна, не сегмент. Нулевые ответы → health не берёт π, иначе 10 таймаутов выглядели бы как конверсия 24ч. Health ∈ [f, 1] при enabled; выключен → множитель 1.

Пример. 1 approve 20 с, 1 reject 10 с, 1 expired 500 с, дефолтный YAML. p90 по {10, 20} = 19 с (expired не входит). â = 6/13, t̂ = 0.1875, ĉ = 0.5, latency = 581/600, q ≈ 0.656, score ≈ 0.313, health (answered > 0) = 0.25 + 0.75 · 0.6875 = 0.765625. Десять одних expired: availability = 0.30, health = 0.475.

YAML

metrics:
  window: { max_observations: 50, recent_observations: 10 }
  smoothing:
    prior_strength: 10.0
    approval_prior: 0.5          # не conversion_24h
    timeout_prior: 0.10
    timeout_prior_strength: 5.0
    segment_min_size: 5
    segment_confidence_strength: 10.0
  combination: weighted_sum
  components:
    approval_rate: { enabled: true, weight: 0.40 }
    availability:  { enabled: true, weight: 0.25 }
    acceptance:    { enabled: true, weight: 0.15 }
    latency:       { enabled: true, weight: 0.20, bad_p90_sec: 600 }
  multipliers:
    health: { enabled: true, floor: 0.25, exponent: 1.0,
              availability_weight: 0.60, acceptance_weight: 0.40 }

Новая метрика

  1. Ключ и источник в Routing::Metrics::Inputs (session, catalog, window, runtime, operation).
  2. Откуда берётся значение: поле каталога, счётчик сессии, компонента окна, runtime, операция.
  3. Комбинация: дописать в METRICS существующей стратегии или класс в SoftGoals::GOALS + вес в YAML.

Не складывайте разнородные шкалы в один weighted_sum, если функция другая: дефицит доли — не то же, что 2q − 1 окна. Функция комбинации и есть стратегия. Hard-constraint по-прежнему отдельный слой: метрика может дублировать сигнал (RPM в load и в Intensity), но skip ≠ score.

Гарантии

  1. Hard важнее: низкий health не skip.
  2. enabled health ≥ floor · base, если base > 0.
  3. Timeout-шторм не наследует conversion_24h в health.
  4. Один исход — одна строка; поздний approve не держит timeout в p90.
  5. Веса включённых компонент суммируются в 1; combination применяется в Catalog.
  6. Неизвестный ключ YAML — ошибка загрузки.
  7. Fallback и каскад: spacepayments вне смеси; отказ промежуточного портит его окно.
