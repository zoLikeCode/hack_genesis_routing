Архитектура payout routing

Operation
  → Runtime snapshot + revision
  → hard constraints для всех провайдеров
  → Ranker допустимых внешних провайдеров
  → атомарная reservation с повторной проверкой hard constraints
  → provider.call(operation_id, idempotency_key)
       approved → commit
       rejected → rollback → свежий snapshot → следующий провайдер
       expired  → reservation удерживается → status-check, без fallback

Online-принцип

Операции обрабатываются по одной в порядке created_at. Будущая очередь не используется. Каждый результат изменяет runtime-счётчики и доступен следующему snapshot. Устаревшая revision заставляет повторить выбор.

Reservation и timeout

Reservation сразу занимает count, amount, daily capacity, requisite и RPM. Обычный provider outcome записывается вместе с settlement под одним mutex. При timeout reservation остаётся активной. Поздний approved коммитит её, rejected/cancelled освобождает; прошлые маршруты не переигрываются. После исчерпания status-check задача переходит в manual_review с удержанной reservation.

Доли и fallback

Count включает подтверждённые и удержанные reservations текущего запуска. Volume включает стартовый дневной approved и reservations. Отказ откатывает оба значения. Исторический CSV не входит в знаменатели долей. Fallback имеет target 0, учитывается в фактическом распределении, но никогда не конкурирует в soft ranking.

strategy_score ∈ [0,1]
Σ enabled normalized_weight = 1
total = Σ(weight × strategy_score)
winner = max(total), затем меньший priority, затем имя
